# Home page: the film

The `/` page is a **55.5 s film** (Three.js, real captures of a chalet) **driven by scrolling**, dressed in the game's interface (chat, typing bubble, pause menu, `/title` titles, an HTML hotbar on top of the canvas), followed by **the site**: the live 3D model moves into a panel next to the text (hero, three steps, sharing, three questions, footer). The film's state is a **pure function of time**; scrolling, the wheel, touch and keys only feed deltas to the clock (`scrub.js`).

The prototype (reports, decisions, control tests) lives in `docs/marketing/v0/`: **a local folder, ignored by Git**. This document describes what is integrated into the repository.

## Integration design

1. `HomePage` renders `HeroFilm`. The `hero.html` markup is JSX (`HeroMarkup.tsx`, same classes and same `id`s: the film code and its CSS address them as is).
2. The markup is rendered **only once** (memoized component without props), **in French**: that is the prerender language and the first one rendered on the client. The film then rewrites the `data-i18n` elements in the visitor's language (`apply()` of the i18n bridge). React and the film therefore never write the same node twice; no hydration error.
3. What depends on the session or the language lives in components that follow the app context: the site's bar (`SiteNav.tsx`, the same as every page's: menus, account, language, install button, phones' panel) and `HeroParts.tsx` (footer links, the three questions).
4. The **film is 100% client side**: `import('../hero/hero.js')` in a `useEffect`. The prerender contains the whole site (titles, steps, FAQ, "The film, in words"), readable without JavaScript and without WebGL. Without WebGL 2 (or with `?nowebgl=1`), the scene is never loaded: the site is the page and the still image of the model is the panel.
5. `hero.js` is no longer a script that runs on import: `mountHero({ i18n, capturesUrl })` returns `dispose()`. Every `window` and `document` listener goes through an `AbortController`, the frame loop stops, and `scene.dispose()` releases the WebGL context. Going to `/installation` and back mounts a fresh film.
6. The **film CSS is global** (it styles `html`, `body`, `main`, `ul`, `button`…, and `html.is-scrub` locks document scrolling). It is therefore in a `<style>` rendered by `HeroFilm`: it only exists while the home page exists. It is imported as `?raw` (raw text, not `?inline`): Vite's CSS minifier rewrites some gradients (`linear-gradient(0deg, …)` becomes an equivalent reversed gradient) and the screen quantization then shifts by a few levels over entire rows; raw, the film frames are pixel-identical to the prototype's. `first-paint.js` (`prepareRoot`) sets the phase, layout variables and film class on `<html>` **before the first paint** and returns `restore()`, which gives `<html>` back its previous class, style and `data-*`. For the prerender, `scripts/prerender-web.mjs` injects the same code as an inline script before the `/` markup (`firstPaintScripts` exported by `prerender.tsx`); React renders no `<script>`.
7. Without JavaScript, `.site` is visible (hiding is done by `html.scene-on .site`, a class set only by the first paint).
8. The i18n bridge (`src/lib/hero-i18n.ts`, 100% covered) gives the film `t`, `apply` and `onChange` on top of the app's `translate()`: same keys (the English text), same catalogs, **a single language picker** (the app's, `LanguagePicker`, in the bar from 700 px; under 700 px in the phones' panel, drawn only while it is open). `<title>`, description and social tags stay with `RouteMetadata`. The player is always called "Efe".
9. Assets: `apps/web/public/hero/` (GLB captures, fonts, icons, fallback images, served as is under `/hero/`); only the 4 scene PNGs (`src/hero/assets/mc/`) go through Vite (`new URL(…, import.meta.url)`, hashed). `scene.js` receives `capturesUrl: '/hero/captures/'` and `captures: 'v2light'`, plus `fetchGlb` (optimized delivery of the captures from `/hero/captures-opt/`, generated by `bun run hero:assets`, see [film-assets-pipeline.md](film-assets-pipeline.md)).

## Resyncing with the prototype

The prototype is the source (`docs/marketing/v0/web/`). To pick up a new version: copy `hero.js hud.js phase.js scrub.js site.js scene.js characters.js look.js life.js sky.js backdrop.js anim/ mcui/hotbar.js`, then **reapply the adaptations**:

- `hero.js`: the whole body in `export function mountHero(host)` (module state made local); `on(target, …)` with `signal` for every `window`/`document` listener; `loop` stops if `disposed`; `dispose()`; `i18n = host.i18n` (no more `createI18n`, no more language selectors); `capturesUrl` and `captures: 'v2light'`; `console.info` for the expected WebGL fallback.
- `scene.js`: the capture delivery hook (the film's `fetchGlb`, `glbFetcher`, three lines marked "hero-assets anchor": see [the film asset pipeline](film-assets-pipeline.md)); `hero.js` passes `host.fetchGlb`. `scene-anchor.test.js` fails if a copy from the prototype erases them (the film would silently fall back to the full GLBs).
- `hud.js`: `ctx.signal` on both `document` listeners.
- `film.css`: concatenation of `mcui.css`, `hero.css`, `site.css`; `url('mcui/…')` and `url('assets/mc/…')` paths rewritten to `/hero/…`; fallback `.ttf` fonts removed; `.site` visible by default and hidden by `html.scene-on .site`; a section of app additions at the end of the file.
- `HeroMarkup.tsx`: regenerated from `hero.html` (`data-i18n` attributes kept, texts in JSX), then the dynamic parts replaced by `HeroParts`.
- Translations: new prototype keys (`web/i18n/*.json`, sources in `web/i18n/src/catalog-src.mjs`) must be added to the 8 complete catalogs and to the variants in `apps/web/src/i18n/locales/`; `catalogs.test.ts` requires the same keys, the same `{parameters}` and the same proper nouns (Minecraft, Mojang, AFK…).
- Then rerun `bun run web:check` and the browser checks.

**Deliberate divergence from the prototype (v13, 05/11/2026)**: the momentum law, the arrival wheel flick and the return (next section) only exist in the app (`scrub.js`, `hero.js`, `film.css`, and in `scene.js` the quiet moment for loading the stages). A copy from the prototype would erase them: reapply them; `scrub-elan.test.js` fails if they are missing.

## Scrolling: momentum, arrival wheel flick, return (v13, 05/11/2026)

Andy's request: more human control (acceleration, deceleration), and a visitor who arrives and scrolls down right away should see the site almost instantly, without losing their place in the film.

- **Momentum law** (`law: 'elan'`, the page's law; `?law=slew` restores the v10 law for comparison). Each input keeps its distance (1 px = 1/280 s of film, as before) but spends it on a speed that rises in ≈ 40 ms then falls back to zero along a finite curve: 200 ms for small touchpad deltas (the system already adds its own momentum), up to 750 ms for a wheel notch, 900 ms for a finger flicked on release (≥ 350 px/s). Close notches add up: the film accelerates, then glides to a clean stop. An input in the opposite direction brakes (the film "gets caught").
  - What does not change: beyond the cap (12× since v13b, see below), the excess is **discarded** (ongoing momentum is reduced, nothing is set aside or caught up later: the v8 flaw Andy rejected remains impossible); the flash guards apply to the glide (it counts as driving); no randomness (same inputs, same trajectory).
  - No light effect is tied to speed: a speed-driven edge darkening was tried and then removed in review, because a back-and-forth wheel made it flicker more than 3 times per second, out of reach of the guards.
- **Frantic wheel (v13b, Andy's feedback: "much more accelerated, go further")**: the driving cap goes from 3× to **12×** (the v10 law keeps 3×), and a fast-turned wheel gets up to **4× more film per pixel** (from 700 to 2,600 px/s, measured over 250 ms in the same direction; a direction change restarts at 1×). An opposite input brakes hard (only 5% of the momentum remains). The day/night transition is the only place where speed would make the sky flicker: approached at more than 3× from outside, it is **skipped** (the page covers the cut with a fade and momentum continues on the other side; counted with the cuts, 2 per second at most). Slower, or from inside, the v10 guard (1 cycle per second) applies. Measurement: with a fast-turned wheel (one 100 px notch every 40 ms), the whole film rewinds in 4.7 s under Node and 5.5 s in Chromium GPU (before: about twenty seconds).
- **Smooth film ending**: the scene prepares stages S1 to S4 in the background (≈ 100 to 150 ms of main thread per stage) and used to wait for a "quiet moment", including "the film has passed 16.3 s". After a wheel flick landing at 52.3 s, it prepared them during the camera rise (19 frames of 50 to 167 ms measured). Now, from the last cut (50.5 s) to the site, during the glide and while the visitor drives fast, only a film at rest counts as quiet: preparation happens on the site, once the visitor has arrived. Measurement after the fix: no stage during the ending, frames at a 17 ms median (a few isolated spikes of 50 to 100 ms in the headless browser, also present on the second run).
- **Arrival wheel flick** (`flick`, `?flick=0` to turn it off). As long as the visitor has not taken control of the film (nothing upward, no pause, no chapter, no timeline, no key), a first downward wheel or finger gesture (≥ 24 px within 300 ms) takes them to the site: the film rushes for 0.34 s (up to 8×, but **never** into the day/night transition, the rewind wave or within 0.65 s of a cut: the run stops at the first barrier), the image zooms in (1 → 1.08) while the HUD fades, then the last frame, at the same zoom, covers the cut and flies off (1.08 → 1.24 and a fade in 0.42 s), then the film lands at 52.3 s (after the last freeze and the last cut) and plays its ending at 2×: the camera leaves the fire and rises to the whole model under "That evening was kept by Minemories" (1.6 s), then the glide sets it in its panel (1 s). In total ≈ 3 s from gesture to site. The keyboard never triggers this jump (it drives). During the run and the zoom-out, inputs are ignored; on arrival, the document stays locked while the wheel or finger is still sending momentum (`html.is-settling`, 280 ms of calm).
- **Return**: any exit to the site from the middle of the film (wheel flick, "Skip the film", Escape, End, external scrolling) **keeps the position** and the intent (playing or paused). At the top of the site, once the 120 px slack is passed, scrolling up replays the zoom-out in reverse (0.9 s), the ending frame dives toward the visitor (zoom and fade in 0.5 s), the film arrives underneath at the exact spot it was left (1.06 → 1, then its HUD comes back) and holds for 1.6 s before resuming. The rest of the gesture that requested the return is ignored (inputs less than 280 ms apart): its momentum does not rewind the film. Focus left in the site goes to the play button; after a wheel flick, focus left on a film control goes to the page title. "Watch the film again", a chapter or the timeline forget the position; a direct link to the site, or a film watched to the end, keep the v10 rewind from 55.5 s.
- **Reduced motion**: unchanged (stations, no momentum, no arrival jump). If the clock switches to reduced motion during a jump or a return, it finishes immediately where it was heading. Existing limitation: the page does not yet pass on a preference change made after loading.
- **Rejected or bounded in review** (20 confirmed defects, all fixed except the limitation above): a mostly horizontal gesture does not count; `touchcancel` does not launch; a finger flicked on arrival performs the jump; the jump turns off once the end of the film is reached or within 0.5 s of the site.
- **Tests**: `scrub-elan.test.js` (S17 to S26: notch distance, frantic wheel and day/night skip, rise and stop, acceleration, nothing set aside beyond 3×, guards S8 to S10 replayed under the new law, a run that enters no sensitive passage from nine starting points, return, 600 deterministic random sequences); `scrub.test.js` keeps S1 to S16 on the v10 law.
- **Measurements** (headless Chromium GPU, 1440 × 900): waiting for the cover takes one frame (15 to 16 ms) both ways; mean luminance on a wheel flick: one drop (toward the ending's night) then one rise (the camera climb), a single pair over more than a second, under the 2-per-second rule; on return, the ending frame fade does happen frame by frame (opacity 1 → 0 and zoom 1 → 1.1 in 0.45 s, read from the DOM; the recording video skips this fade).
- **Not verifiable here**: the feel. The trajectories are proven under Node and the full path (arrival, site, return at 3.40 s) ran in headless Chromium GPU; it needs to be tried with a real mouse, a real touchpad and a phone. Test parameters: `?law=slew`, `?flick=0`, `?k=`, `?idle=`.

## Loading screen (08/11/2026)

The first visit to `/` opens on a **world-loading screen** in the spirit of the game's (Andy's reference: a "Minecraft Java world loading screen" video, 0:03 then 0:12): a dark dirt background, a chunk map that fills from the centre with its percentage above it, then the dirt leaves **block by block** from the map outwards and reveals the film. It replaces the Steve-mining-an-ore loader, archived in `scripts/boot-screen/legacy/` (README there to restore it).

- **Where**: the three `<!-- boot:begin -->` … `<!-- boot:end -->` blocks of `apps/web/index.html` (style at the end of `<head>`, `#boot` markup before `<div id="app"></div>`, inline script before the `main.tsx` module), outside `#app`, so hydration and the prerender (`<div id="app"></div>` replaced as before) are untouched. They are **generated**: `bun run boot:screen` (`node scripts/boot-screen/gen.mjs`; `--check` fails if the file is stale). The runtime is `scripts/boot-screen/chunk-screen.mjs`, inlined function by function; `gen.test.mjs` (in `scripts:test` and the web CI job) checks index.html matches the generator and covers the map model, the pace, the estimate, the reveal order and the screen's life cycle on a fake page, including the inline script exactly as written into index.html (run in `node:vm`).
- **Our own drawing, no game file**: the 16 × 16 dirt tile is generated from a seeded PRNG: a smooth 8 × 8 noise mixed half and half with per-texel grain (small clumps like soil, without showing the tile's repeat), ranked into six shades taken from the brightness quantiles of the reference frame (equal steps on red, green and blue; mean ≈ `#1f1610`, spread ≈ 5 per channel like the capture), plus four pebbles. It is inlined once, as a ~360-byte indexed PNG (stored without compression, so every zlib writes the same bytes), on `#boot::before` with `image-rendering: pixelated`; the script reads it back from that CSS for the reveal. One scale, `--c`, sets both the map cell and the dirt texel, like the game's interface scale: 3 px up to 900 px of viewport height, 4 px, then 5 px from 1300 px, so a tile is 48, 64 or 80 px. The map (38 × 38 cells, like the game's interior) is a canvas painted by the script; its growth is described under **Map** below. It sits exactly at the centre of the viewport at every size (the game draws it slightly lower; the owner asked for an exact centre on 08/11/2026). The percentage is positioned above it without moving it. The percentage uses the site's game font (`MM Boot` face on the already preloaded `mm-minecraft-regular.woff2`), white with a `#3f3f3f` one-texel shadow, 6 cells above the map. The font only draws whole pixels at multiples of 8 px (1024 units per em, 128 per texel), so it is 8 px at the 3 px scale (the capture's "100%" is 29 × 9 px, ours 23 × 7) and 16 px above. Inline weight: 11,393 bytes for the three blocks, under the 12 KB cap of the tests (the Steve loader weighed 42 KB). The generator squeezes the script (`squeeze` in `gen.mjs`: no space next to an operator or a bracket outside string and template literals, line breaks kept), which saves about 1.3 KB; without it the map model would be over the cap.
- **Progress**: real milestones from the app, eased in between. `HeroFilm.tsx` reports them with `lib/boot-progress.ts` as `mm:boot-progress` events on `window` (`detail` = a floor in 0..1): app mounted 15 %, film code loaded 30 %, scene built and asking for its first capture 50 %, first capture downloaded 80 % (whichever it is: `S0`, or another one when the landing opens on a link to a section; `withBootProgress` wraps the film's `fetchGlb`, so `hero.js` stays a copy of the prototype). Before the app is ready the bar shows the further of the app's progress (the last milestone creeping towards the next quarter, or a time-based estimate) and the fill pace (see **Timing**), never faster than that pace and never past 95 %. Since the pace runs ahead of the milestones on every load measured, the milestones do not change what is shown today; they are kept (the listener costs nothing) for a pace that may be slowed later. It reaches 100 % only once the page has loaded **and** `mm:ready` has fired (the film's first image is drawn, `hero.js` `signalReady`); after a late `mm:ready` it climbs from 95 % at twice the fill pace (1 % per 20 ms, never a jump), holds 400 ms, then the reveal plays. If the film's code fails to arrive, `HeroFilm.tsx` sends `mm:ready` itself (`signalPageReady`, the same pair as `signalReady`), so the prerendered page shows at once rather than after the 20 s stop.
- **Main-thread stalls**: the percentage and the map are drawn by the page's main thread, which the app's start and the film block for one to two seconds (parsing the first capture, building the scene). No browser API can animate a canvas or a text while the main thread is busy, and delaying the film would only make the load longer. So the screen runs on its own clock, which moves 50 ms per frame at most: during a stall the map simply freezes, then the fill resumes where it was, so no part of the animation (the off-centre start, the recentring) is skipped; the fill then ends later by the stall's length. Measured on the built site (warm cache, no delay, after the map tuning): at 375 × 812 the map froze at 0 % from about 0.04 s to 1.9 s, then resumed and played the rest of the fill (100 % at 5.9 s, reveal at 6.3 s, gone at 7.4 s); at 1280 × 720, 100 % at 5.3 s, reveal at 5.7 s, gone at 6.8 s.
- **Map** (rewritten 08/11/2026: Andy found the previous map did not grow like the video's, reading as pixels building in circles on several axes, like a cube; it grew round, jagged rings; then tuned against a frame-by-frame comparison). Measured on the reference video (`build/ref/dense/`, 30 fps, 4.5 s to 12.5 s): the map starts black; grey appears alone as a square of about 14 cells around the player, off-centre in the video (13 cells left and down), then the view recentres. **Ours starts centred and never moves** (Andy, 10/11/2026: the map must pop straight in the middle, not in the black square's bottom-left corner and then slide; the off-centre start and its 0.4 s recentring, `mapShift`, `C.from` and `C.move`, are gone). About 100 ms after the grey a dark-blue dot of 1 to 2 cells grows in it, then a green ring, then a white dot inside the green; `C.at` (13 % of the fill) is still where the growth model switches from that first stage to the steady growth. Then every front is a **square** (Chebyshev rings, never a disc, a cross or a star):
  - **Growth**: the core's area, not its side, grows at a steady rate after a slow start (`mapSize`), so its side slows down near the end, as in the video. Its blue outer side is within 1.5 cells of the video's at every measured point from 8 % of the way (the video: 6.7, 9, 12, 15, 17.3, 18.7, 20.7, 22.7, 23.7 cells); just after the recentring ours is 6 cells against the video's 4 to 5, so the white dot shows before the recentring. The grey stays 7 rings ahead of the core and reaches the border with it, just before 100 % (about 95 %).
  - **Sides**: each side of each front (`mapSides`) steps one ring at a time on its own seeded schedule (give or take a third of a ring), so about a third of the frames are one cell off square, like the video's. The next ring fills in as a strip along the side from a seeded corner over the last 0.3 ring before its step lands; the blue and green rings wrap round it. A strip shows from 2 cells, never on a front of 2 rings or less, and at most two strips per front at once (the two that started first), so a small front never reads as a cross. No inward bite, no pit.
  - **Rings**: the blue ring is painted 2 pixels wide with its inner third green (`paintMap`), so blue reads thinner than green, about 2 : 4 px against the video's 2 : 3.5.
  - **Speckles** (`mapSpeck`): light-grey cells (`#ddd`, the game's "finishing" chunks) just inside the green, in the ring the core reached last (40 % of its cells at 100 % of the fill, fewer early), a few one ring deeper, re-drawn every 150 ms.
  - **100 %**: the shapes snap at once to exact squares: white 20 × 20, one green ring, one blue ring, 7 rings of grey (38 cells); the last few speckles fade out over the 400 ms hold.
  - The model is seeded (`mapPlan` once, then `mapLevels(q)` per frame), so the same map plays on every visit and the tests can check it: squares within two cells with no spike, pit or hole, at most two strips per front, ring order, pace against the video's table, clean squares at 100 %, never going back.
- **Timing**: **every visit plays the whole animation** (owner request, 08/11/2026), even when the page is cached and ready at once: `#boot` covers the page in plain dirt colour (`#1f1610`) from the first paint, so the prerendered landing never flashes before it, and the dirt texture and the map fade in over 200 ms. The map stays black for 350 ms (`C.lead`), then the percentage follows the app (milestones, estimate) but never faster than a straight line from 0 to 100 % over 4 s (`C.fill`, `bootPace`), and never reaches 100 % before `mm:ready`. So a fast load shows 0 → 100 % in 4.35 s of the screen's clock (plus any main-thread stall, see above), holds 400 ms (the clean squares), then the 1.1 s reveal: about 5.9 s in all; a slow load holds at 95 % at most until ready. **The film waits for the screen** (Andy, 10/11/2026): everything loads under the screen (the scene, the first capture, the first image), but the film's clock only starts when the percentage reads 100 %. The screen then sets `data-mm-boot-full` on `<html>` and sends `mm:boot-full` on `window` (once; also when it leaves without reaching 100 %: safety stop, removal); `hero.js` arms its clock (`loopScrub`, `scrub.rebase`) or starts the guided film (`afterBoot`) only then, and waits 21 s at most if the screen never says so. Measured on the dev server (1280 × 720): ready at 2.75 s, the film held at t = 0 until 100 % at 6.5 s, then playing; the reveal uncovers it about 1.9 s in (it used to be 4 to 5 s in). Safety: the script fades the screen after 20 s whatever happens, and the CSS hides it after 20 s even without JavaScript; a page that becomes ready within the last 1.1 s before that stop gets the short fade, never a reveal the CSS stop would cut.
- **Header after a flick** (Andy, 10/11/2026): a strong first wheel or swipe (the flick: rush, cover, glide, site) is a way out of the film, so the site's header (solid, menus, menu button) comes in over 0.3 s as the rush starts (`html.is-leaving`, set on the scrub's `flick`/`burst` event), instead of following `--g` once the glide starts 2 to 3 s later. `is-leaving` ends when the site is reached (the site's own rules take over) or when the visitor comes back to the film, which gives the film's header back. Measured at 1440 × 900: links fully shown 0.4 s after the wheel (they were at 2.6 s).
- **Reveal** (≈ 1.1 s): the dirt is copied once into a single canvas (the CSS background is dropped in the same frame, at the same tile size), then each tile shrinks towards its centre in four steps (a quarter of the tile each, so whole texels) over 200 ms, barely darkening (12 % at most), and is cleared; tiles start along square fronts around the map (like chunks loading around the player) with a little seeded randomness. Each frame only redraws the tiles in their 200 ms window. The map scales to 1.3 and fades in sync, and the percentage fades in its first 120 ms (CSS). `pointer-events: none` during the reveal. Once the screen is gone, its listeners are removed (`AbortController`) and the full-screen canvas is freed. **Reduced motion** (the system setting or the site's own option, `html[data-mc-motion=reduced]`): the map still fills over 4 s but starts centred (no recentring; if the site's option is set after the script started, the view jumps to the centre instead of moving), then a 250 ms fade instead of the reveal.
- **Scope and accessibility**: only `/` plays it. The prerender (`scripts/prerender-web.mjs`) drops the three blocks from every other page, `app.html` and `404.html`, and the script removes `#boot` on any other path (development server); other pages signal `mm:ready` from `PageFrame.tsx`. `role="status"` with a visually hidden "Loading Minemories…" / "Chargement de Minemories…" (by `html[lang]`); the map and the percentage are `aria-hidden`; nothing takes focus.
